# 🔝 Top 10 Improvements (Highest Impact First)

1. **Cancel with `trigger="file"` no longer fires `printFinished` or the document-level `printCancel`**
   - **Category:** compliance
   - **Why it matters:**
     - This is the intended fix: the user is back on the upload card, so the flow isn't over.
     - But a host that closes its UI on `printFinished`, or an iframe bridge that maps it to `printCancelled` (as the samples use), will no longer hear about a Cancel from the printer dialog.
     - For the `button` and `custom` triggers, window listeners now receive one `printCancel` per cancel instead of two.
   - **Evidence:**
     - `src/components/ezp-printing/ezp-printing.tsx:136-147`
     - `src/components/ezp-printer-selection/ezp-printer-selection.tsx:292-298`
     - `samples/07-iframe-file-trigger.html:312`
   - **Action:** *Check the iframe bridge's event mapping before release and note the change in the changelog.*

2. **The host panel can still scroll on short screens**
   - **Category:** correctness
   - **Why it matters:** the widget now tops out at 362px. But backend-switcher's `PrintNowPanel` keeps `overflow-y-auto` inside `max-h-[80vh]`, so below about 630px of screen height, or when the "print from any app" column is taller, the panel itself still scrolls.
   - **Evidence:** backend-switcher `src/components/layout/PrintNowPanel.tsx:166-196`
   - **Action:** *Follow up in backend-switcher: give the widget a height via `--ezp-upload-height` and remove the panel body's scroll.*

3. **The PR is over the 500-line guideline**
   - **Category:** maintainability
   - **Why it matters:** 697 changed lines. That's mostly tests (331); there are 314 lines of source.
   - **Evidence:** `git diff --numstat origin/main...HEAD`
   - **Action:** *Review commit by commit; each ticket is self-contained.*

4. **Tooltip placement arithmetic is only partly covered by automated tests**
   - **Category:** tests
   - **Why it matters:**
     - The side choice (`pickTooltipSide`) and the clipping-ancestor walk (`visibleArea`) are now unit-tested, including the step across a shadow root.
     - The final offset arithmetic in `placeTooltip`, including the scale correction, still needs real layout, so it's checked only by the headless browser runs, not by CI.
   - **Evidence:** `src/components/ezp-file-name/ezp-file-name.tsx:185-213`
   - **Action:** *Add an e2e test (`npm run test.e2e` runs in CI) that opens a tooltip in a scrolled list and asserts its rect.*

5. **Changing `anchor` while a tooltip is open leaves stale state**
   - **Category:** correctness
   - **Why it matters:**
     - Switching `parent` → `container` keeps the inline `top`/`bottom`, which override the CSS placement.
     - Switching `container` → `parent` attaches no scroll listeners.
     - No consumer changes `anchor` at runtime today.
   - **Evidence:** `src/components/ezp-file-name/ezp-file-name.tsx:107-113`
   - **Action:** *If `anchor` becomes dynamic, add `@Watch('anchor')` that clears `tooltip.style` and re-runs `watchTooltipOpen`.*

6. **Mouse-wheel input over an open tooltip scrolls the page, not the list**
   - **Category:** maintainability
   - **Why it matters:** the tooltip's containing block is outside the scroller. The scroll still closes the tooltip, so this is harmless, just unexpected.
   - **Evidence:** `src/components/ezp-printer-selection/ezp-printer-selection.scss:143-149`
   - **Action:** *Accept, or close the tooltip on `wheel` over it.*

7. **The shadow-root step of the scroll-listener walk isn't exercised**
   - **Category:** tests
   - **Why it matters:** in the spec the host sits in the light DOM, so the `ShadowRoot → host` branch of `watchScroll`, which makes listening work inside real consumers, is only verified in the browser. The new `visibleArea` walk does have this step covered.
   - **Evidence:**
     - `src/components/ezp-file-name/ezp-file-name.tsx:237-250`
     - `src/components/ezp-file-name/ezp-file-name.spec.tsx`
   - **Action:** *Mount `ezp-file-name` inside a shadow-rooted test component and scroll that root.*

8. **`onScroll` wiring isn't asserted**
   - **Category:** tests
   - **Why it matters:** both scroll handlers and `firstVisibleChild` are unit-tested, but no spec proves `#files-list` / `#file-list` actually bind them.
   - **Evidence:**
     - `src/components/ezp-upload/ezp-upload.tsx:264`
     - `src/components/ezp-printer-selection/ezp-printer-selection.tsx:1091`
   - **Action:** *Dispatch a `scroll` event on the rendered list in a spec page and assert `firstVisibleFile` changes.*

9. **The dev toolchain has known vulnerabilities (they're also on `main`)**

   - **Why it matters:** `npm audit` reports 58 (53 high, 5 moderate, 0 critical). They're all in development tooling: `jest`, `@types/jest`, `puppeteer`, `stylelint`, `stylelint-order`, `stylelint-prettier` and `patch-package`. None of these ship in the bundle, and this PR doesn't change the lockfile.
   - **Evidence:** `npm audit`, run 2026-10-20 on `7ebf5ff`
   - **Action:** *Track as a separate dependency-update ticket (the fixes are semver-major).*

10. **Prettier drift (also on `main`)**

# 📝 Additional Reviewer Notes

- **Peer-review finding (@tp-carlosmartins), fixed in `8712145`:**
  - **Problem:** on the upload card a tooltip opening upwards could be cut off by `#body`.
  - **Repro:** Chromium, 420px, 10 files, two-line bubbles.
  - **Measured, after the fix:**

    | Row above the first fully visible row | Before | After |
    |---|---|---|
    | at the end of the list | opened downwards, 0px hidden | same |
    | 3px in view | opened downwards, 0px hidden | same |
    | 30px in view | opened upwards, 7px of 48px hidden | opens downwards, 0px hidden |

  - The first two cases were already fixed by `7ebf5ff`. The reviewer's 13px / 34px numbers were measured on `839071d`.
- **Findings from the first AI pass, fixed in `7ebf5ff`:**
  1. A row with only a sliver in view counted as the topmost row, so the row actually read first opened its tooltip upwards, over the header. `firstVisibleChild` now requires a row to be at least half in view.
  2. Measured placement mixed screen and CSS pixels, so the tooltip drifted under a scaled host. It now converts with the measured scale (checked at `scale(0.8)`: the gap is 4.8 screen px, which is 6 CSS px).
  3. An open tooltip didn't react to a window resize. It now closes on resize as well as on scroll.
  4. A node moved while its tooltip was open came back open with no listeners. `disconnectedCallback` now closes the tooltip.
- **Checked and found not to be problems:**
  - stale `firstVisibleFile` after adding or removing files (scroll clamps, and the lists remount)
  - `componentDidRender` loops or flicker
  - the `top: 0` origin measurement with the upload card's 1px border
  - listener pairing (`closeTooltip` is a stable arrow function)
  - `printDismiss` bubbling across shadow DOM
  - the `max-height` math in both components (content-box vs border-box)
  - focus-ring clipping
- **Manual checks:** headless Chromium against the built bundle with stubbed printer APIs, light and dark:
  - 11 long-named files in Print Options and 10 in the upload card
  - tooltips at the top, middle and end of each list
  - the downward tooltip on the topmost row in view
  - tabbing to the last row
  - Cancel / X / "Remove files"
  - a host scaled to 80%
- **Not verified:** inside the real backend-switcher host, or against real printer hardware.
